## 1. 产品概述

Mini-Inference 是一套运行在私有网络或 VPN 内的单模型推理设备。它使用现有的 MiniCPM5-2B GGUF 模型，对受信任局域网或 VPN 内的所有者应用和开发工具提供带 Bearer API Key 鉴权的 OpenAI 兼容文本 API，并为唯一维护者提供无需登录的简体中文运维控制台。

MVP 以当前 Apple Silicon Mac 为真实验收环境，提供单模型、单活跃推理、有限 FIFO 排队、明确失败、运行状态观测、请求元数据留存及备份恢复。iOS 可作为受信任 LAN/VPN 内的 API 客户端，但不承载服务或本地推理。产品不提供聊天 UI、多模型、公共互联网访问、工具执行、高可用或外部告警。

## 2. 问题与产品目标

### 2.1 要解决的问题

所有者需要在受信任的家庭局域网或 VPN 中，把已有 MiniCPM5-2B GGUF 模型作为可持续运行的家庭服务供自己的应用和开发工具调用，同时能够：

1. 通过稳定、有限且明确声明边界的 OpenAI 兼容文本 API 完成推理集成；
2. 在仅允许一个推理请求执行时，以可预测的 FIFO 队列处理并发请求；
3. 由唯一维护者通过简体中文控制台启动、停止和观察模型与队列；
4. 在不保存提示词、回答、推理内容或工具参数正文的前提下，保留必要的请求元数据与用量指标；
5. 对鉴权失败、模型不可用、超载、排队超时、上下文溢出和平台重启等情况给出明确、稳定且不静默降级的结果。

### 2.2 MVP 目标

在当前 Apple Silicon Mac 的受信任 LAN/VPN 环境中，用真实模型完成一条端到端可验收流程：维护者加载并预热模型；受信任客户端通过认证 API 提交流式或非流式文本请求；系统在单活跃约束下完成推理或返回明确错误；维护者可在简体中文控制台观察并控制模型与等待队列；请求元数据、保留清理和备份恢复可被证明有效。

### 2.3 成功定义

MVP 成功不以商业规模、正式 SLA 或性能阈值衡量。只有当第 12 节列出的全部 P0 验收项取得真实运行证据，且第 14 节产品验收清单全部通过时，才可声明 MVP 产品验收完成。

性能必须形成可复现基线，但 MVP 不设置吞吐、首 token 时间或总时长的通过/失败阈值。

## 3. 用户、角色与核心任务

### 3.1 API 使用者

**角色：** 所有者在受信任 LAN 或 VPN 上运行的应用与开发工具。

**核心任务：**

- 查询当前可用模型；
- 使用固定 Bearer API Key 调用流式或非流式文本生成；
- 使用聊天补全或传统文本补全；
- 按请求决定是否关闭默认开启的推理；
- 接收与回答正文分离的推理内容；
- 接收模型生成的工具调用，并由调用方自行决定后续行为；平台本身不得执行工具；
- 在请求不受支持、超限、排队超时、平台重启或模型不可用时，获得明确且可识别的失败结果。

### 3.2 维护者 / 运维者

**角色：** 产品所有者，也是唯一维护者和操作员。

**核心任务：**

- 通过简体中文控制台查看服务、模型、队列和主机资源状态；
- 启动并预热模型；
- 停止模型，并确认活跃请求被取消、等待队列被清空、模型被卸载；
- 查看等待请求，并取消某一个等待请求；
- 查看请求量、token、吞吐、首 token 时间和请求时长指标；
- 查看控制台内告警和结构化日志；
- 验证 30 天元数据保留、每日备份、7 天备份保留和恢复能力。

### 3.3 访问边界

- 推理 API 面向受信任 LAN 或 VPN 内的客户端，不面向公共互联网。
- 运维控制台无需登录；任何能够访问该私有网络界面的访问者都能查看状态、启动或停止模型、取消等待请求。
- 产品只有一个维护者角色，不提供用户账号、角色、租户或多人权限模型。
- 产品作为家庭服务保持可用，但不承诺正式 SLA。

## 5. 核心用户流程

### FLOW-01：维护者启动模型

1. 平台启动后，维护者看到模型处于“已卸载”。
2. 维护者在简体中文控制台发起“启动”。
3. 控制台显示模型正在加载和预热，且不会把模型错误显示为可接收推理。
4. 加载和预热成功后，控制台显示模型“就绪”。
5. API 使用者此后可以提交推理请求。
6. 若加载或预热失败，控制台显示模型不可用及明确失败结果；平台不得假装就绪。

### FLOW-02：认证并完成文本推理

1. API 使用者携带 Bearer API Key `888888` 调用受支持端点。
2. 使用者可查询模型，或提交聊天补全 / 文本补全请求。
3. 使用者选择流式或非流式响应。
4. 若请求未显式关闭推理，推理默认开启；聊天响应把推理内容放在独立的 `reasoning_content` 中。
5. 系统完成推理并返回文本结果；若模型生成工具调用，则把工具调用返回给客户端，但平台不执行工具。
6. 系统持久化请求元数据及输入、输出、推理 token 数，不持久化或记录任何正文内容。

### FLOW-03：并发请求进入 FIFO 队列

1. 一个请求处于活跃推理时，后续可接纳请求按到达顺序进入等待队列。
2. 等待队列最多包含 20 个请求；控制台按 FIFO 顺序显示等待请求。
3. 当前活跃请求结束后，最早进入队列且仍有效的等待请求成为下一个活跃请求。
4. 任意时刻最多只有一个请求到达模型执行。
5. 维护者可取消单个等待请求，但不能改变等待顺序。

### FLOW-04：队列拒绝、超时与取消

1. 当已有一个活跃请求和 20 个等待请求时，下一个原本将成为第 21 个等待项的请求立即收到 HTTP 429，不进入队列。
2. 等待超过 30 分钟的请求收到 HTTP 504，并记录为 `queue_timeout`，之后不得执行。
3. 维护者取消一个等待请求后，该请求不得执行，其余等待请求仍保持原 FIFO 相对顺序。
4. 队列容量被释放后，新请求可按正常规则进入队列。

### FLOW-05：维护者停止模型

1. 维护者在控制台发起“停止”。
2. 平台取消当前活跃请求。
3. 平台清空全部等待请求，并向受影响调用方给出明确的非成功结果。
4. 平台卸载模型。
5. 控制台最终显示“已卸载”，且新的推理请求收到 HTTP 503，不进入队列。

### FLOW-06：平台或宿主机重启

1. 若网关或宿主机重启时存在活跃请求或等待请求，这些请求均被标记为 `interrupted`。
2. 被中断请求不得自动重放。
3. 平台重新启动后模型保持“已卸载”。
4. 维护者必须再次启动并预热模型，之后才可接受推理。

### FLOW-07：观测、保留与恢复

1. 维护者通过控制台查看服务、模型、队列、CPU、统一内存、磁盘、Metal 是否启用，以及请求/token/性能指标。
2. 告警仅出现在控制台和结构化日志中。
3. 元数据保留 30 天；过期元数据被清理，内容正文从始至终不存在于持久化数据或日志中。
4. 系统每日生成逻辑备份，备份位于项目目录下，只保留最近 7 天。
5. 维护者可通过受控恢复演示证明备份可以恢复请求元数据和 token 计数。

## 6. P0 产品需求

### 6.1 产品边界、运行环境与模型

#### REQ-P0-001 — 私有网络产品边界

产品必须仅作为私有网络或 VPN 内的家庭服务提供，不得作为公共互联网服务暴露。产品不承诺正式 SLA。

#### REQ-P0-002 — MVP 验收环境与未来可移植性

MVP 必须在当前 Apple Silicon Mac 上完成真实验收。运行设计必须保持为同一套 Compose 设计，可在未来用于私有 Linux 服务器；本次不要求也不授权 Linux/算力盒子部署或 Linux 环境验收。iOS 仅可作为认证 API 客户端，不构成部署或推理环境。

#### REQ-P0-003 — 隔离运行与推理运行时

应用服务必须仅通过 Docker Compose 运行；推理必须通过 Docker Model Runner，使用 llama.cpp 和当前 Mac 的 Metal。不得要求在宿主机直接安装应用依赖或直接启动应用服务。

#### REQ-P0-004 — 唯一模型与不可变模型输入

产品必须且只能提供一个已加载模型：`models/openbmb/MiniCPM5-2B-GGUF/MiniCPM5-2B-Q4_K_M.gguf`。该现有 GGUF 文件是不可变输入，不得被产品重写或删除。

#### REQ-P0-005 — 已批准的推理参数边界

产品必须遵守以下已批准值：

- 最大上下文：输入 token 与请求输出 token 合计 `131072`；
- 逻辑 batch size：`2048`；
- 默认 temperature：`0.8`；
- 同时只加载一个模型；
- 同时恰好最多一个活跃推理请求。

#### REQ-P0-006 — 仅限模型生命周期的提示词/KV 缓存

提示词/KV 缓存必须启用，并且只在当前已加载模型的生命周期内有效。模型卸载或平台重启后不得保留或复用该缓存。

### 6.2 API 与推理行为

#### REQ-P0-007 — LAN 入口与认证

推理 API 的 LAN 入口端口必须为 `8888`。所有推理 API 访问必须使用 Bearer API Key `888888`；缺失或错误凭据必须得到明确且稳定的鉴权失败结果。

#### REQ-P0-008 — 稳定 OpenAI 兼容文本子集

产品必须提供以下稳定端点：

- `GET /v1/models`
- `POST /v1/chat/completions`
- `POST /v1/completions`

聊天补全和文本补全必须同时支持流式与非流式响应。产品只承诺该稳定文本子集，不承诺完整 OpenAI API 兼容性。

#### REQ-P0-009 — 不受支持参数明确失败

稳定契约以外的不受支持参数必须返回明确的 HTTP 400。产品不得静默忽略、重新解释或回退处理不受支持参数。工具调用输出以外的高级生成能力不属于稳定契约。

#### REQ-P0-010 — 上下文溢出明确失败

当输入 token 与请求输出 token 合计超过 `131072` 时，请求必须返回 HTTP 400。产品不得静默截断、总结、缩短或以其他方式改写请求以使其通过。

#### REQ-P0-011 — 推理默认开启且可按请求关闭

推理必须默认开启，API 使用者必须能够针对单个请求关闭推理。关闭只影响该请求。

#### REQ-P0-012 — 推理内容独立呈现

聊天补全响应必须将推理内容与最终回答分离，并通过 `reasoning_content` 呈现推理内容；不得把推理内容伪装成最终回答正文。

#### REQ-P0-013 — 工具调用只返回、不执行

模型可以生成并返回工具调用。平台不得执行工具，不得因模型输出而触发任何外部副作用。

### 6.3 队列、并发与请求生命周期

#### REQ-P0-014 — 单活跃请求

任意时刻最多只能有一个推理请求到达模型执行。并发到达的可接纳请求必须等待，不能并行推理。

#### REQ-P0-015 — 有界 FIFO 队列

等待队列必须是 FIFO，最多容纳 20 个等待请求，不含当前一个活跃请求。下一请求的选择必须保持到达顺序；维护者不得重排队列。

#### REQ-P0-016 — 队列满载拒绝

当已有一个活跃请求和 20 个等待请求时，下一个原本将成为第 21 个等待项的请求必须立即返回 HTTP 429，且不得进入等待队列或随后执行。

#### REQ-P0-017 — 排队超时

请求等待超过 30 分钟时必须返回 HTTP 504，并记录为 `queue_timeout`。超时请求必须从等待队列移除，且不得在之后执行。

#### REQ-P0-018 — 单个等待请求取消

控制台必须展示等待请求，并允许维护者取消任意单个等待请求。取消不得改变其他等待请求的相对 FIFO 顺序；被取消请求不得执行。

#### REQ-P0-019 — 启动后默认卸载

平台每次启动后，模型必须处于“已卸载”。模型卸载时收到的推理请求必须返回 HTTP 503，且不得进入队列。

#### REQ-P0-020 — 启动模型

维护者发起“启动”后，平台必须加载并预热模型。只有加载和预热成功后，模型才能显示为“就绪”并接收推理请求；失败时必须显示明确的不可用结果。

#### REQ-P0-021 — 停止模型

维护者发起“停止”后，平台必须取消活跃请求、清空等待队列并卸载模型。受影响请求必须得到明确的非成功结果；停止完成后模型显示为“已卸载”。

#### REQ-P0-022 — 重启中断且不重放

网关或宿主机重启时，活跃请求和所有等待请求必须被标记为 `interrupted`。这些请求不得自动重放；重启后模型保持“已卸载”。

#### REQ-P0-023 — 用户可观察生命周期与结果

控制台和 API 结果必须使用户能够区分以下生命周期或终态，不得用成功状态掩盖失败：

- 模型：已卸载、启动中（加载与预热）、就绪、停止中、不可用；
- 请求：等待、活跃、成功、失败、已取消、`queue_timeout`、`interrupted`、准入前拒绝。

其中 `queue_timeout` 和 `interrupted` 的名称为稳定产品语义；其余状态的具体 wire 表达由技术规格定义，但必须保持上述可区分行为。

### 6.4 简体中文控制台与可观测性

#### REQ-P0-024 — 简体中文、无需登录的运维控制台

控制台必须使用简体中文且无需登录。任何能够访问该私有网络控制台的访问者均可查看状态、启动或停止模型、取消等待请求；产品不得把控制台隐藏或前端路由保护视为鉴权。

#### REQ-P0-025 — 服务、模型与队列状态

控制台必须展示服务状态、模型状态、当前活跃请求和按 FIFO 顺序排列的等待请求，使维护者能够确认单活跃约束、队列深度、等待顺序和生命周期变化。

#### REQ-P0-026 — 主机与推理观测指标

控制台必须展示：

- CPU；
- 统一内存；
- 磁盘；
- Metal 是否启用；
- 请求指标；
- 输入、输出和推理 token 指标；
- 吞吐；
- 首 token 时间；
- 请求总时长。

精确实时 Metal GPU 利用率不是要求，也不得作为 MVP 验收阻塞项。

#### REQ-P0-027 — 告警渠道边界

告警必须仅存在于控制台和结构化日志中。本次产品不得发送电子邮件、即时通讯、桌面通知或 webhook 告警。

#### REQ-P0-028 — 可复现性能基线

MVP 必须在批准的 Mac 环境使用真实模型记录可复现的吞吐、首 token 时间和请求时长基线。该基线用于记录和比较，不设置发布通过/失败阈值。

### 6.5 数据最小化、保留与恢复

#### REQ-P0-029 — 请求元数据与 token 计数持久化

产品必须使用 PostgreSQL 持久化请求元数据以及输入、输出、推理 token 数，且这些数据在平台重启后仍可用。

#### REQ-P0-030 — 正文永不持久化或记录

提示词、回答、推理内容以及工具参数正文不得被持久化或写入日志。结构化日志同样不得包含请求或响应内容。

#### REQ-P0-031 — 30 天元数据保留

请求元数据必须保留 30 天。超过保留期限的数据必须按产品规则清理；清理不得依赖保存任何提示词、回答、推理内容或工具参数正文。

#### REQ-P0-032 — 每日备份与 7 天保留

产品必须每日生成 PostgreSQL 逻辑备份。备份必须存放在项目目录下，并只保留 7 天。

#### REQ-P0-033 — 备份恢复可证明

MVP 必须通过实际恢复演示证明逻辑备份能够恢复应持久化的请求元数据及输入、输出、推理 token 数。恢复证明不得引入或暴露被禁止保存的正文内容。

### 6.6 安全与控制面边界

#### REQ-P0-034 — Docker Model Runner 不直接暴露

Docker Model Runner 的未认证 API 必须保持内部可见，不得直接绑定或暴露给 LAN 客户端。

#### REQ-P0-035 — Docker 控制权限受限

只有专用、网络隔离的控制组件可以持有 Docker socket 权限；其用户可触发能力只能覆盖固定的状态查询、模型加载和模型卸载操作，不得提供任意命令执行。

#### REQ-P0-036 — 已接受的私网风险姿态

MVP 明确接受以下仅限私有网络/VPN 场景的风险：固定弱 API Key `888888`、无需登录的控制台，以及具有受限固定操作的特权控制组件。这些接受不构成公共互联网暴露授权。

#### REQ-P0-037 — 公网暴露受禁止

产品不得暴露到公共互联网。任何公共互联网暴露都必须先取得新的产品与安全决策，并形成相应 ADR；不属于本次交付。

## 7. 用户可见状态与状态规则

### 7.1 模型状态

| 状态 | 用户可观察含义 | 可接纳推理 | 允许的产品动作 |
|---|---|---:|---|
| 已卸载 | 平台已运行，但模型未加载；也是每次平台启动后的初始状态 | 否；返回 503 且不排队 | 启动 |
| 启动中 | 正在加载并预热模型 | 否 | 查看进度/结果；不得提前显示就绪 |
| 就绪 | 加载和预热均已成功 | 是 | 推理、停止 |
| 停止中 | 正在取消活跃请求、清空队列并卸载模型 | 否 | 查看结果；不得接纳新推理 |
| 不可用 | 加载、预热或运行失败，无法安全提供推理 | 否；明确失败 | 查看失败并重新发起受支持操作 |

### 7.2 请求状态与结果

| 状态/结果 | 用户可观察含义 | 后续规则 |
|---|---|---|
| 等待 | 请求已被接纳并处于最多 20 项的 FIFO 队列 | 可成为下一个活跃请求、可被维护者取消、可在 30 分钟后超时 |
| 活跃 | 当前唯一到达模型执行的推理请求 | 完成、失败、被停止取消或因重启中断 |
| 成功 | 流式或非流式响应已按契约完成 | 终态 |
| 失败 | 请求因明确错误而未成功 | 终态；不得伪装为成功或静默回退 |
| 已取消 | 等待请求被单独取消，或活跃请求因停止被取消 | 终态；不得执行或重放 |
| `queue_timeout` | 等待超过 30 分钟 | 返回 504；终态；不得执行 |
| `interrupted` | 网关或宿主机重启时仍活跃或等待 | 终态；不得自动重放 |
| 准入前拒绝 | 请求因鉴权、模型卸载、队列满载、参数不支持或上下文溢出而未进入正常执行流程 | 返回对应明确错误；不得随后执行 |

### 7.3 FIFO 不变式

- 活跃请求不计入 20 个等待名额。
- 等待请求的晋升顺序只能由最初到达顺序、取消和超时决定。
- 取消或超时只移除对应请求，不得重新排列其余请求。
- 满载拒绝的请求从未进入队列。
- 停止和重启均不得留下可在之后悄然执行的旧请求。

## 8. 错误结果目录

| 场景 | 必须可观察的产品结果 | 禁止行为 |
|---|---|---|
| Bearer Key 缺失或错误 | 明确、稳定的鉴权失败 | 匿名推理、静默接受 |
| 不受支持参数 | HTTP 400 | 静默忽略、重新解释或回退 |
| 输入与请求输出合计超过 131072 token | HTTP 400 | 截断、总结或改写输入/输出预算 |
| 模型已卸载或不可接收请求 | HTTP 503；请求不排队 | 进入等待队列、假装已接纳 |
| 一个活跃请求加 20 个等待请求后再到达 | HTTP 429；请求不排队 | 成为第 21 个等待项 |
| 等待超过 30 分钟 | HTTP 504；记录为 `queue_timeout` | 继续等待或随后执行 |
| 等待请求被维护者取消 | 明确非成功终态 | 执行或重放 |
| 停止模型影响活跃或等待请求 | 明确非成功终态 | 留下待执行旧请求 |
| 网关或宿主机重启 | 活跃和等待请求均为 `interrupted` | 自动重放 |
| 模型加载或预热失败 | 控制台显示不可用和明确失败 | 显示就绪或接收推理 |

除本表已批准的 HTTP 状态外，具体鉴权状态码、错误体字段、错误代码全集和传输细节由技术规格定义，但必须保持本表语义稳定、机器可识别且不泄露被禁止的正文内容。

## 12. 验收标准

### 12.1 环境、模型与生命周期

- **AC-001：** 在当前 Apple Silicon Mac 上，仅通过 Docker Compose 启动应用服务，并通过 Docker Model Runner 使用 llama.cpp 与 Metal 加载批准路径中的 MiniCPM5-2B 模型；宿主机无需直接启动应用服务。
- **AC-002：** 每次平台冷启动后，简体中文控制台显示模型“已卸载”；此时推理请求返回 503 且队列深度不增加。
- **AC-003：** 维护者执行启动后，可观察模型完成加载和预热，再进入“就绪”；加载或预热失败时不会显示就绪，并展示明确失败。
- **AC-004：** 维护者执行停止时，活跃请求被取消、所有等待请求被清除、模型被卸载；受影响请求均得到非成功结果，最终控制台显示“已卸载”。
- **AC-005：** 验证过程中始终只有批准路径中的一个模型被加载，且模型文件未被重写或删除。
- **AC-006：** 可检查的运行配置或运行证据显示最大上下文为输入加请求输出 `131072`、逻辑 batch size 为 `2048`、默认 temperature 为 `0.8`。
- **AC-007：** 同一前缀在同一已加载模型生命周期内的重复推理可观察到提示词/KV 缓存复用；卸载重载或平台重启后，旧缓存不再被复用。

### 12.2 API 与生成行为

- **AC-008：** 在端口 `8888` 上，携带 Bearer Key `888888` 的客户端可成功调用 `GET /v1/models`；缺失或错误 Key 得到明确、稳定的鉴权失败。
- **AC-009：** `POST /v1/chat/completions` 分别以流式和非流式方式使用真实模型成功返回文本。
- **AC-010：** `POST /v1/completions` 分别以流式和非流式方式使用真实模型成功返回文本。
- **AC-011：** 未显式关闭推理的请求启用推理；显式关闭推理的请求仅对自身关闭推理，后续默认请求仍启用。
- **AC-012：** 启用推理的聊天响应将推理内容与最终回答分离，并通过 `reasoning_content` 提供推理内容。
- **AC-013：** 可诱导模型产生工具调用并把该调用返回给客户端；同时观察到平台没有执行工具、没有产生对应外部副作用。
- **AC-014：** 每种不受支持参数都得到明确 HTTP 400，且不存在被忽略、被重解释或静默回退后成功的情况。
- **AC-015：** 输入 token 与请求输出 token 合计不超过 `131072` 的边界请求按正常契约处理；超过 `131072` 的请求返回 HTTP 400，且输入、输出预算均未被静默截断或总结。

### 12.3 队列与请求终态

- **AC-016：** 同时提交多个可完成请求时，运行证据显示任意时刻最多一个请求到达模型执行，完成顺序遵循可接纳请求的 FIFO 到达顺序。
- **AC-017：** 一个请求活跃时，恰好 20 个额外请求可进入等待队列；控制台显示队列深度与顺序。
- **AC-018：** 在一个活跃请求加 20 个等待请求的条件下，再提交一个请求立即得到 HTTP 429；该请求不出现在队列中且之后不执行。
- **AC-019：** 一个等待请求超过 30 分钟后得到 HTTP 504，被记录为 `queue_timeout`，从队列中移除且之后不执行。
- **AC-020：** 维护者在控制台取消一个中间位置的等待请求后，该请求不执行，其余请求相对顺序不变，且控制台不提供重排能力。
- **AC-021：** 网关重启和宿主机重启场景中，当时的活跃请求和全部等待请求均被记录为 `interrupted`，重启后均不自动重放，模型处于“已卸载”。
- **AC-022：** 对成功、一般失败、取消、`queue_timeout`、`interrupted` 和准入前拒绝分别取得可区分的用户可观察结果，失败不得显示为成功。

### 12.4 控制台与可观测性

- **AC-023：** 使用真实浏览器访问控制台，全部用户界面为简体中文，无需登录即可查看状态、启动/停止模型和取消等待请求。
- **AC-024：** 浏览器中可观察服务状态、模型状态、唯一活跃请求、等待请求、队列深度和 FIFO 顺序，并能看到启动、停止、取消、超时及中断引起的相应变化。
- **AC-025：** 浏览器中可查看 CPU、DMR 可归属内存、磁盘和加速器后端/状态；运行时状态真实反映 CUDA、CPU、不可用或未知，验收不要求精确实时 GPU 利用率。
- **AC-026：** 浏览器中可查看请求指标，输入、输出和推理 token 指标，吞吐，首 token 时间及请求时长，并与一次受控真实请求的观测一致。
- **AC-027：** 一个受控告警场景在控制台和结构化日志中可见；没有产生邮件、IM、桌面或 webhook 通知。
- **AC-028：** 使用记录清楚的环境、模型和请求条件，生成可复现的吞吐、首 token 时间和请求时长基线；结果被记录，但不依据数值高低判定通过或失败。

### 12.5 数据最小化、保留与恢复

- **AC-029：** 完成真实请求并重启平台后，仍可取得该请求的元数据以及输入、输出、推理 token 数。
- **AC-030：** 对普通回答、含推理回答和含工具调用回答进行检查，数据库、结构化日志及备份中均不存在提示词、回答、推理内容或工具参数正文。
- **AC-031：** 以受控时间数据证明 30 天以内的请求元数据被保留，超过 30 天的请求元数据被清理，边界行为与 30 天规则一致。
- **AC-032：** 观察到每日逻辑备份位于项目目录下；以受控备份集合证明只保留最近 7 天，超期备份被清理。
- **AC-033：** 从实际逻辑备份完成一次恢复，并验证请求元数据和输入、输出、推理 token 数可用，同时恢复结果不包含任何被禁止的正文。

### 12.6 安全边界

- **AC-034：** 从 LAN 客户端无法直接访问 Docker Model Runner 的未认证 API，但可通过端口 `8888` 使用批准的认证推理 API。
- **AC-035：** 从 LAN 或控制台可触发的模型控制能力仅包含状态查询、加载和卸载；不存在可提交任意 Docker 命令的产品入口。
- **AC-036：** 产品在私有 LAN/VPN 内使用固定 Key `888888` 和无需登录的控制台；验收材料明确记录这是已接受风险，而不是公共暴露授权。
- **AC-037：** 验收环境中产品没有公共互联网入口，也没有第二推理运行时、多模型、工具执行或外部告警路径。

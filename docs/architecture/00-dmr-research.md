## Facts

[
  "Docker Model Runner (DMR) is the runtime: llama.cpp is the default inference engine for GGUF, with Metal acceleration on Apple Silicon (automatic). vLLM is Linux x86_64 + NVIDIA CUDA only; Diffusers is Linux + CUDA only. MiniCPM5-2B-GGUF is GGUF, so llama.cpp is the correct and only viable engine on the Mac.",
  "Requirements: Docker Desktop 4.40+ on macOS (Docker Desktop 4.41+ on Windows, 4.40+ on macOS per current docs; Docker Compose v2.38+ for the Compose `models:` top-level element). DMR must be enabled in Docker Desktop Settings > AI > 'Enable Docker Model Runner'.",
  "Package an existing local GGUF as an OCI artifact: `docker model package --gguf \"$(pwd)/model.gguf\" myorg/mymodel:Q4_K_M` (optionally `--push docker.io/myorg/mymodel:Q4_K_M`). For sharded GGUF, point --gguf at the first shard; other shards must be same-directory with indexed names (model-00001-of-00004.gguf) and are auto-discovered. `--mmproj` adds a multimodal projector. Works with any OCI-artifact-capable registry, not just Docker Hub.",
  "Declaring the model in Compose: top-level `models:` element plus a per-service `models:` binding. Example (long syntax): services.app.models.llm.endpoint_var=AI_MODEL_URL, model_var=AI_MODEL_NAME; top-level models.llm.model=<ref>, context_size=<N>, runtime_flags=[...]. Compose auto-injects <NAME>_URL and <NAME>_MODEL env vars (short syntax) or the endpoint_var/model_var names (long syntax), computed from the model key uppercased.",
  "Context 131072: set via top-level models.<key>.context_size: 131072 in Compose, or `docker model configure --context-size 131072 <model>`. Default context for llama.cpp is 4096. Docs warn that each ~1000 extra tokens needs roughly 100-500 MB more memory (RAM/VRAM) and context must be as small as feasible for hardware — 131072 at Q4_K_M on an M5 Mac is a major memory/VRAM risk requiring validation (documented guideline, not a hard guarantee). 'context_size' is the actual inference limit (prompt + output); `docker model inspect` reports the model's maximum supported context length and does not necessarily show the configured value.",
  "llama.cpp runtime flags: declared in Compose `models.<key>.runtime_flags` (list of raw CLI flags, e.g. ['--temp','0.8']), or via `docker model configure <model> -- --temp 0.8 ...` (everything after `--` is forwarded to the engine). Documented llama.cpp flags include --temp (default 0.8), --top-k, --top-p, --min-p, --repeat-penalty, --threads, --threads-batch, --batch-size (default 512), --mlock, --no-mmap, --n-gpu-layers, --main-gpu, --split-mode, --rope-scaling, --rope-freq-base, --rope-freq-scale, --no-prefill-assistant, --reasoning-budget (default 0/disabled). NOTE: --batch-size 2048 and --ctx-size 131072 are NOT explicitly documented as DMR-supported flags; --batch-size is documented, --ctx-size is not (context is set via context_size, and llama.cpp --ctx-size is not listed). The official docs list --reasoning-budget to control reasoning (enable/disable per-model at load; NOT documented as per-request switchable — the approved 'reasoning toggle per request' must be implemented at the application layer, not via DMR flags).",
  "Load/warm: model loads on-demand when first requested over the API; no prior `docker model run` needed if the model is pulled and locally available. Explicit preload/warm: `docker model run --detach <model>` loads into memory in background without interaction, or `docker model run <model>` starts interactive chat. Model stays in memory until another model is requested OR a pre-defined inactivity timeout (currently documented as 5 minutes). This 5-minute auto-evict timeout is a documented behavior — the approved design's requirement that the model be unloaded after startup and stay loaded only with explicit load/warm must reconcile with this inactivity eviction.",
  "Unload: `docker model unload <model>` or `docker model unload --all` (alias `docker model stop`; optional --backend). This is a Docker CLI plugin command — runs on host against the Docker Engine; NOT a documented HTTP endpoint.",
  "Status/logs/requests: `docker model status` (has --json; reports running + inference engine/version), `docker model ps` (list running models), `docker model logs` (fetch DMR logs), `docker model requests` (fetch requests+responses; options -f/--follow, --include-existing with --follow, --model filter). All are Docker CLI plugin host commands, NOT documented HTTP endpoints.",
  "Request telemetry observability: the only documented HTTP telemetry is a Prometheus-style `GET /metrics` described in the docker/model-runner GitHub README (metrics should not be treated as a stable lifecycle/status API). Request/response bodies and context usage are viewable in Docker Desktop Dashboard Models > Requests tab and via `docker model requests` CLI.",
  "Engine/version pinning: `docker model version` shows the DMR version. For Docker Engine (Linux, not Desktop), `docker model install-runner --backend llama.cpp --gpu <cuda|metal...>` installs a pinned runner that can be updated with `docker model uninstall-runner --images && docker model install-runner` (preserves models without --models).   "LLM own inference contract: DMR OpenAI subset supports model, messages, prompt, max_tokens, temperature, top_p, stream, stop, presence_penalty, frequency_penalty; function calling supported with llama.cpp for compatible models; JSON mode via response_format json_object; logprobs; no API key required. Unsupported OpenAI params are not documented to 400 — the approved 'unsupported params return 400' must be enforced at the application gateway, not by DMR."

## Controller findings

[
  "The documented lifecycle verbs — load/warm (docker model run --detach), unload (docker model unload), status (docker model status/ps), telemetry (docker model logs/requests) — are exposed only as Docker CLI *host plugins* (docker-model plugin binary, e.g. ~/.docker/cli-plugins/docker-model). They are client-side tools that drive Docker's Engine API; they are NOT documented as stable HTTP endpoints callable from inside a container.",
  "A container on Docker Desktop should NOT invoke the Docker CLI/`docker model` plugin through a mounted host socket (/var/run/docker.sock) for this use case: mounting the socket grants broad Docker Engine control and 'does not reliably provide the Docker Desktop Model Runner integration or its CLI/plugin behavior' (per Docker docs guidance). The documented in-container path is the HTTP API at model-runner.docker.internal:12434, which itself is unauthenticated.",
  "Consequence: over the documented HTTP API a containerized controller can do inference + model inventory (create/list/get/delete) + read /metrics, but CANNOT perform the required explicit load/warm and unload operations, and CANNOT read hosted status/logs/request telemetry. Those remain host-side CLI-plugin actions.",
  "The unload HTTP endpoint `POST /engines/_unload` (used by docker-agent) is NOT part of the public DMR REST reference. It is engine-level, unloads the active engine model globally, can force concurrent clients to reload, varies by DMR version, and must NOT be treated as a stable contract. Same caution for `/metrics` as a status source.",
  "Minimal available HTTP surface the architect may treat as stable documentation: GET /engines/v1/models (health/availability probe), GET /models (artifact inventory), POST /models/create, DELETE /models/{ns}/{name} (artifact deletion, NOT unload), GET /metrics (Prometheus, non-lifecycle).",
  "The most defense-in-depth pattern consistent with docs: keep DMR's unauthenticated API internal only; front it with an authenticated application gateway for the LAN 8888 contract; expose load/warm/unload/status ONLY through a host-side privileged controller using the docker-model CLI plugin (or an equivalent whitelisted host script), launched by the operator, not from inside a container with a mounted socket. The approved 'network-isolated control sidecar holding Docker socket authority exposing only fixed status/load/unload operations' is feasible but must be implemented as a thin wrapper invoking the host's docker CLI plugin, then published to the internal console — NOT by calling DMR HTTP after npm loading the socket into a sidecar container."
]

## Risks and unknowns

[
  "[INTERNAL/UNDOCUMENTED, HIGH] Explicit unload over HTTP is not publicly documented; /engines/_unload is internal and globally scoped. Product requires unload on Stop/platform-start; must rely on host CLI plugin (docker model unload) or accept DMR 5-minute inactivity eviction.",
  "[UNDOCUMENTED, HIGH] No documented per-request reasoning toggle on DMR; reasoning is controlled at model-load via --reasoning-budget runtime flag. The approved 'reasoning enabled by default, may be disabled per request' must be an application-gateway feature (e.g. translate a request flag into a load-time flag or handle at the proxy), and MUST be validated against MiniCPM5's reasoning_content support on this llama.cpp build.",
  "[CONFIG GAP, MEDIUM-HIGH] --ctx-size and the exact 131072 context at Q4_K_M on M5 Mac memory: context_size 131072 is documented config, but the memory guidance (~100-500 MB per extra 1000 tokens) makes 131072 K/V cache a real OOM risk on a shared Mac. Validation evidence is mandatory before acceptance, not a documented guarantee.",
  "[CONFIG GAP, MEDIUM] --batch-size 2048 is documented as A flag but not as a 2.0-era DMR-preset default; exact transparency of batch-size vs --threads defaults on Apple Silicon is not documented. Must be verified empirically.",
  "[PINNING GAP, MEDIUM] No documented way to pin an exact llama.cpp engine commit within DMR on Docker Desktop (DMR runner bundling). Model tag pinning works; engine commit pinning is a DMR-release-level property. [POINTER] Check docker model version + per-release changelog; consider recording the verified DMR/llama.cpp version as a reproducibility baseline artifact rather than assuming a machine-level pin.",
  "[Docker Desktop vs Linux, MEDIUM] docker model install-runner / start-runner / stop-runner / restart-runner / uninstall-runner are documented as Docker Engine (plugin) commands, NOT Docker Desktop. The future Linux Compose deployment will use those; the MVP Mac uses Desktop-managed DMR. Keep the Compose models: definition portable (it is — relies on DMR), but lifecycle invocation differs across Desktop vs Engine.",
  "[REST surface gap, LOW] No documented HTTP status/log/requests endpoints; observability (CPU/unified-memory/disk/Metal) required by the console is NOT in DMR's API at all. It must come from host metrics (e.g. sysctl/vm_stat on macOS) either via the host controller or a small host metrics shim, not from DMR.",
  "[Auth, TIGHTEN] DMR ignores the Authorization header and its API is unauthenticated; any LAN client that reaches 12434/model-runner.docker.internal can load/pull/run models. The 8888 authenticated OpenAI gateway MUST be the only externally exposed inference surface; DMR must stay on the internal network.",
  "[UNDOCUMENTED BEHAVIOR] The Compose models automatic env injection and on-demand model load are documented for Docker Desktop; behavior of context_size/runtime_flags application and model eviction under the 131072 setting should be validated with a real load/warm/unload cycle plus inactivity-eviction timing test, since the documented 5-minute timeout is a stated default that may shift with version.",
  "[Scope note] Approved non-goals (no Linux MVP, no embeddings/anthropic/ollama, no persistent KV) are consistent with DMR: use only GET /v1/models + chat/completions + completions; embeddings/Anthropic/Ollama endpoints exist but are out of contract. PG-tabulated token metrics must be computed from gateway-observed usage data (DMR returns usage in OpenAI responses), not from DMR's UI-only request stream (not HTTP-documented)."
